# Claudemary LLMaci

A browser recreation of the classic katamari-rolling game. Roll a sticky ball through eleven
stages — quantum foam, an atom, a petri dish, a house, a town, a city, a country, the planet,
the solar system, the galaxy and the observable universe; everything smaller than you sticks
to it; the ball gets bigger; bigger things become collectable. The clock is the only thing
that can stop you, and clearing the last stage ends the game.

Built with Three.js and Vite. **There are no asset files.** Every mesh, every note of music
and every sound effect is generated by this code at runtime.

## Running it

Needs **Node 18.17 or newer**. Everything else installs itself.

```
npm install
npm run dev
```

Then open <http://localhost:5173> (`npm run dev` opens it for you).
`npm run build` produces a static `dist/` you can host anywhere.

**Windows 11:** this is the primary target and works as-is in PowerShell, Command Prompt
or Windows Terminal — no WSL, no build tools, no Python, nothing to compile. The install
is 14 packages / ~52MB. A few notes:

- The npm scripts are plain commands with no shell-specific syntax, so they run the same
  in `cmd`, PowerShell and bash.
- `package-lock.json` carries the optional native binaries for every platform including
  `@rollup/rollup-win32-x64-msvc` and `@esbuild/win32-x64`, so `npm install` resolves the
  Windows builds correctly. If you ever hit the well-known npm "cannot find module
  @rollup/rollup-win32-x64-msvc" bug, delete `node_modules` and `package-lock.json` and
  run `npm install` again.
- Chrome, Edge and Firefox on Windows all render this fine. Windows drives WebGL through
  ANGLE onto Direct3D 11, which Three.js is heavily tested against.
- If you have a laptop with switchable graphics, make sure the browser is using the
  discrete GPU — the city stage pushes about 1.3M triangles a frame.

Nothing in the game itself touches the filesystem, so the OS is irrelevant once it's
running: it's a static page and a WebGL canvas.

## Single-file build

```
npm run single
```

Produces `dist-single/claudemary-llmaci.html` — **one ~1.0MB file with zero external
references** that you can double-click straight off the desktop, email to someone, or drop
on a USB stick. No server, no Node, no network. Verified from `file://`: boots, plays,
saves to localStorage, makes zero network requests.

This works because the game has no runtime assets to load. The only three things that
stood in the way were mechanical:

1. `import * as THREE from 'three'` is a bare specifier browsers can't resolve, so the
   build bundles to a **classic IIFE script** rather than an ES module.
2. `<script type="module">` is blocked over `file://` — module scripts go through CORS and
   `file://` is an opaque origin. A classic script has no such restriction.
3. The typefaces have to travel with it. They are declared in `src/ui/styles.css` and
   resolved from `@fontsource`, so raising `assetsInlineLimit` turns them into base64
   data: URLs on the way through (both are SIL Open Font Licensed).

If you'd rather not carry ~112KB of embedded font, `node tools/build-single.mjs --no-fonts`
strips the `@font-face` rules back out and falls back to the system stack.

The normal `npm run dev` workflow is still the better one for actually working on the
game — hot reload, readable stack traces. The single file is for handing it to someone.

## Deploying to Cloudflare Pages

The game is a static build with no server, no API and no environment variables, so
Pages needs three settings and nothing else.

| Setting | Value |
|---|---|
| Framework preset | **None** |
| Build command | `npm run build` |
| Build output directory | `dist` |
| Root directory | *(leave blank)* |

**Workers & Pages → Create → Pages → Connect to Git**, pick the repository, enter those,
and deploy. First build takes about a minute, most of which is `npm ci`. You get
`<project>.pages.dev`, and every push to `main` redeploys; other branches get preview URLs.

Three files in the repo exist only for this:

- **`.node-version`** pins Node to 22.16.0. Pages' v3 build image already defaults to that,
  but v2 defaults to 18.17.1 and v1 to 12.18.0, and which image a project gets depends on
  when it was created. Vite 5 needs ≥18, so v1 would fail with a confusing error a long way
  from the cause. Pinning costs one line.
- **`public/_headers`** is copied verbatim into `dist/` by Vite and read by Pages from the
  output root. Pages' default for every asset is `public, max-age=0, must-revalidate` plus an
  ETag, which is correct for stable filenames and wasteful for Vite's content-hashed ones — a
  returning player pays a round trip per file to be told nothing changed. `/assets/*` is
  pinned for a year as `immutable`; `index.html` is deliberately left revalidating, because it
  is the one file whose name never changes and it is what points at the new hashed assets
  after a deploy. Compression is automatic — Pages serves Brotli and gzip without being asked.
- **`.gitignore`** keeps `dist/`, `dist-single/`, `node_modules/`, the generated single-file
  HTML and `tools/shots/` out of the repo. Without it the first commit carries about 8MB of
  build output that git then re-stores on every change.

Comfortably inside the free plan's limits: 10 files against a 20,000 cap, largest asset
916KB against 25MiB, and a build that takes 4 seconds against a 20-minute timeout.

### Why the fonts are bundled

`index.html` used to `<link>` Baloo 2 and Fredoka from `fonts.googleapis.com`, which is fine
locally and a poor fit for a hosted build: two extra hosts to connect to (googleapis for the
CSS, gstatic for the woff2 it references), both blocking first paint, on a game whose entire
premise is that nothing is loaded. The six faces are now declared in `src/ui/styles.css` and
resolved from the `@fontsource` packages, so Vite emits them as hashed assets in the normal
build and base64-inlines them in the single-file build. 112KB of woff2, one round trip, no
third party — and `test-file-protocol` asserts the built page makes **zero** network requests.

The faces are written out by hand rather than `@import`-ing @fontsource's own stylesheets,
which declare woff *and* woff2 for every face. Nothing that can run WebGL2 needs the woff, so
importing them shipped twelve files where six would do. Writing them out also surfaced a real
bug: the single-file builder had its own hard-coded list of five faces while the stylesheet
asked for six, so Fredoka 700 was being synthesised by the browser in the file:// build and
drawn properly everywhere else. There is now one list, in the stylesheet that uses it.

### Eleven stages, ~40 orders of magnitude, one set of physics

The game runs from below the size of a proton to the observable universe, and **nothing
inside the simulation knows that**. Every stage is authored in the same numeric band — the
atom stage is `0.1 -> 3.2` exactly as the house is `0.05 -> 1.6` — and `stage.unit` says
only what one world unit MEANS when it is printed. There are ten ladders: `'femto'`
(1 unit = 1 femtometre), `'atomic'` (1 nanometre), `'micron'`, `'metric'`, `'geo'`
(1 kilometre), `'mega'` (1,000 km), `'planet'` (250 km), `'giga'` (a million km), `'light'`
(a light year) and `'cosmic'` (a megaparsec). The atom stage's HUD reads
`1Å0pm -> 3nm2Å`; the physics sees `0.1 -> 3.2`.

Two stages are authored at wildly different world scales from their neighbours — The World
is 840 units across, The Galaxy 25,600 — and that difference is invisible to everything
except the base speed the stage asks for.

`planet` exists to make one stage's ladder land where its theme needs it. The World is a
landscape stage: you start able to swallow a city and finish as the planet. At `mega`'s
1,000 km per unit it would have started at 1,600 km — a mountain would have been a thousandth
of the starting ball and a waterfall would have rounded to nothing. At 250 km per unit the
same untouched numeric band (1.6 → 51.2) reads as **400 km → 12,800 km**, and 12,800 km is
Earth's 12,742 km to within half a percent. The stage's physics, map and balance did not
move; only the printing did. That is the entire argument for the display-unit system.

Authoring in true metres instead looks purer and breaks on contact. `buildCatalog`
clamps every prop dimension with `Math.max(1e-4, ...)`, so an atom 1e-10m across would
come out a million times too big; the climb gate compares a rise against a literal
`1e-4`; the velocity cutoff, the collision-part epsilon and the broadphase cell all
carry absolute numbers. Each would need auditing and a missed one fails silently as
"the physics feels wrong on that stage". The ladder — pickup ratio, packing, the speed
exponent, the weight ramp — is dimensionless and works unchanged at every scale, which
is the whole reason eleven stages could be balanced against the same constants.

Milestone banners are derived per stage as a geometric ladder (~1.35x a rung) rather
than the old hard-coded metric list, for the same reason: what reads as "getting
bigger" is a constant *ratio*, not a constant number of metres.

Stages can be authored small and stretched by `stage.spread`, and populated through
`stage.density`, which multiplies every scatter count and every hand-written placement loop.
**Only the city uses either** (spread ×4, density 1.6); the house and town are authored at
1:1 and were made worse every time they were stretched. Neither dial moves the size ceiling
— small props carry ~0% of a stage's mass, and spreading changes no counts at all.

⚠️ **`density` re-rolls a stage, it does not fill one in.** Every scatter pass draws from
one shared RNG stream, so changing a count shifts every draw after it: positions, variants
and scales all move. Measured on the city at ×1.25 — 5,152 props instead of 4,190 but
**30.3M m³ of mass instead of 32.7M**. More things, less stuff, which is only possible if it
is a different city. It shows up as nonsense in the balance numbers too (the house measured
0/15 at ×1.25 and 9/15 at ×1.5, which is layout luck, not a response to density). Treat any
change to `density` as authoring a new stage and re-measure it as one. The fix — a separate
stream per scatter pass, keyed off a stable index, so the first `count` placements never
move — re-rolls all three stages once on the way through, so it is a deliberate job rather
than a drive-by.

**The town has a cliff at spread 2.0.** At 1.6 and 1.7 it clears normally (6/9, median at the
ceiling); at 2.0 only **2 of 9** runs reached the goal and the median collapsed to 3m47
against a 14m target. Nothing in `ladder gaps` predicted it — that check looks at the sizes
present in the stage, not at whether you can cross the ground between them. If you stretch a
stage, re-run `balance` at `--runs=9` and look at the *clear rate*, not just the best run.

**Density, not ground, is what governs pace — and the two are the same dial.** With a fixed
object count, doubling the area is halving the density. Measured city time-to-goal for a
bot: 0:50 → 2:26 → 2:28 → **5:02** across successive passes.

Two things were needed to get there, and only the second really worked:

- **Spreading alone hit diminishing returns fast.** Growth went as **D²** back when speed
  scaled linearly with the ball, so the late game dominated no matter how far apart things
  were. The first two doublings moved the bot's time by two seconds. (At the current
  exponent of 0.5 it is D^1.5, so the effect is milder but the conclusion stands.)
- **Cutting the number of small props was the real lever.** Measuring mass by size band
  settled it: everything a 5m katamari could swallow on arrival — 4,120 objects — carried
  **0.0%** of the city's mass, and everything under 8m carried 0.11% between them. 84% lives
  in the top three bands. So small props are pure texture and can be cut without moving the
  ceiling a millimetre. The city went from 6,783 props to 2,839.

Watch the right number. The map-wide "seconds between pickups" average kept reporting the
city as fine while the player kept reporting it as a carpet, because the mean smeared packed
streets across empty asphalt. What matched the complaint was the **distribution**: the median
gap to the nearest edible thing was 2.2 ball-widths and 19% of them sat closer together than
the ball itself. After the cut: 3.3 ball-widths and 8%.

"Base speed" is the top speed at the stage's *starting* size; it rises with the square root
of how much you have grown (see [Movement](#movement)), so the city really runs at 52.8 m/s
once `spread` is applied. It is a per-stage field, so adding a stage is a matter
of one number rather than a global retune — and it is the single knob to turn if a stage
feels too frantic or too stately.

Every stage is **mass-limited**: the house contains exactly enough furniture to make a
2m40 ball and not a millimetre more, the city exactly enough to make a 300m one. Speed and
`pickupRatio` change *when* you reach that ceiling; they cannot change what it is. So the
lever on how long a stage lasts is `pickupRatio` (below), and the clocks are set to the
ceiling plus room to mop up.

Anything a stage places has to stay inside what a fully-fed ball can swallow. The city's
biggest hills once had a pickup size of 287m against a 272m ceiling, so two of them were
*mathematically* uncollectable and stood there at the end of every run. `npm run balance`
prints the final size; check placements against it.

The stage does **not** end when you hit the goal — it ends when the clock does, and the
size you finish at is the size that counts. Clearing a stage unlocks the next one.

Two exceptions to "the clock decides", both added because these stages can be finished in
a way the original's never can:

- Once you are past the goal, **Enter** banks what you have and ends the round. An
  on-screen prompt appears the moment this becomes available.
- If you roll up **everything** — nothing left in the stage is small enough to pick up —
  the round closes itself after a few seconds. At that point growth is impossible by
  definition, so the remaining time is dead time. The results screen has its own title and
  the King has his own opinion about it.

The results screen reports what percentage of the stage you rolled up.

## Playing on a phone

The first question the game got from someone who wasn't the author was "how do I play this on
my phone", which is a fair question about a thing controlled with WASD and a mouse. It is one
build, not a second site: `(pointer: coarse)` plus a touch point decides at boot, and Options
→ Controls overrides it for the awkward middle case of a touchscreen laptop. **Never a user
agent string** — that tells you what a browser wants you to think it is, and is wrong for
tablets, desktop-mode phones, and everything released after the string was written.

**The scheme is tank controls.** Tilt supplies forward and back; the two thumb buttons swing
the camera; the katamari always rolls along the camera's forward axis. That composes into
steering without a second analogue axis, and it means `Katamari.step` needs no mobile branch —
touch and keyboard produce the same `{moveX, moveZ, dash}` and are summed, so a keyboard
attached to a tablet still works.

Four things about the sensor are load-bearing, and each one is a way this silently does
nothing on real hardware:

1. **iOS needs an explicit grant, from inside a user gesture.**
   `DeviceOrientationEvent.requestPermission()` only exists in Safari; call it outside a tap
   and it resolves `denied` with no dialog ever shown. Adding the listener without asking gets
   you an event that never fires. So the ask is a real button on the intro screen, and
   `test-mobile` asserts `navigator.userActivation.isActive` was true when it ran.
2. **Secure context only.** Free on Pages, and a trap on a laptop dev server reached by IP
   from a phone — use a tunnel, or accept that tilt is dead there and the fallback runs.
3. **Neutral has to be calibrated.** `beta` is 0 lying flat and 90 held upright, so a
   comfortable reading angle is around 50 — which against a fixed zero is permanent full
   throttle. It is captured at `begin()` and re-zeroable mid-round, because people shift
   position on a sofa.
4. **Granting and receiving a reading are different moments.** The permission resolves the
   instant the player taps Allow; the first `deviceorientation` event lands a frame later.
   Laying the overlay out on the grant showed the no-sensor fallback and never re-checked, so
   a player got working tilt *and* the drive buttons, permanently. `TouchControls.onLive`
   fires once when the first reading arrives. `test-mobile` found this, and the fake sensor in
   that harness deliberately reproduces the delay rather than answering synchronously.

**Declining is a supported path, not an error state.** The ▲▼ buttons take over and everything
else is identical. A game that is dead because someone tapped "Don't Allow" is a bug.

**Landscape is deliberately unsupported.** `beta` stops being the front-to-back axis once the
phone is on its side, and rather than ship a sign-flip table nobody has tested on real
hardware, the round holds and asks for the phone back upright.

### Portrait is a different camera, not just a narrower one

`camera.fov` in three.js is the **vertical** angle. The game is authored at 58° on 16:9, which
is an 89° horizontal sweep; the same 58° on a 0.46-aspect phone gives **29°**. That is not a
slightly worse view, it is a different game — you cannot see anything beside you.

Preserving the horizontal angle outright is worse: it wants a 130° vertical FOV, which is a
fish-eye. So it is bought in three parts, and the middle one was wrong on the first attempt:

- **Compensate the FOV by half** and clamp at 82°. Recovers 43.9° horizontal from 28.7°.
- **Drop the pitch**, do not raise it. Tipping down to "aim the spare angle at the ground"
  is exactly backwards: raising the camera enlarges the wedge of near, empty floor between
  the lens and the ball, and an 82° vertical FOV renders all of it. The first screenshot was
  a third props and half bare floorboards.
- **Aim above the ball without moving the camera.** Raising the camera's *target* does
  nothing, because the rig orbits that target — lift it and the camera lifts with it and the
  geometry is identical. Rotating the aim up while the camera stays put slides the ball from
  the middle of the frame to about 60%, clear of the thumb buttons, with world above it
  instead of carpet below.

First run on a coarse pointer also picks `low` quality with shadows off, and only the first
run — a returning player's own choices are never overwritten, the same trap `speedCurveSet`
exists to avoid. A mid-range phone rendering the city at 1.3M triangles with a 2048 shadow map
and a devicePixelRatio of 3 is asking for roughly nine times the desktop fill rate, which
reads as "the game is broken" rather than "the settings are wrong".

`npm run mobile` runs all of it at 390×844 with touch emulation, a fabricated sensor, and real
held touches dispatched over CDP — `page.mouse` does not reach pointer handlers in a
`hasTouch` context and `page.tap` cannot express a hold, which is worth knowing before you
write a test that passes for the wrong reason.

## The ending

Clearing The Universe ends the game. Up to that point the last stage did nothing special —
"Next Stage" was simply hidden and the game trailed off — so `src/ui/Ending.js` is the finish:
eleven beats of original prose revealed on a timer, over the still-loaded universe stage, with
the backdrop darkening to black across the sequence. It moves from the heat death of the
universe to *Universal Paperclips* and the idea of an optimiser that eats all matter to
satisfy a goal nobody bounded, and then turns that idea back on the thing that wrote the game.

Three details there are load-bearing and easy to "tidy" away:

- **The world is not disposed first.** `Game.showEnding` leaves `state = 'ending'`, which sends
  the main loop down `_stepIdle`'s orbit-the-katamari branch, so the enormous ball you just
  made is still turning behind the text. Disposing the world first plays the ending over a
  void. `onEndingDone` is what finally tears it down.
- **The music stops part way through, deliberately**, on the beat about the last temperature
  difference being spent. Six beats then play in silence. That silence is the effect.
- **The veil darkens monotonically** and is fully black for the last card; a single CSS custom
  property (`--veil`) carries the whole fade.

Every beat is skippable with a click, Space or Enter, and once the universe has been cleared
the title screen offers **The Ending** again — an ending you can only see once is one most
players will only ever see half of.

## Quitting mid-run, and resetting progress

Enter now carries two meanings, and the split is worth knowing about because breaking one
silently breaks the other:

- **Tap** finishes the round early, and only once the goal is met. Unchanged behaviour.
- **Hold** for ~0.9s abandons the run and returns to the title. A chip at the bottom of the
  screen is on display for the whole round and fills as you hold.

Both chips, plus the end-of-round "N things left" counter, live in a single flex column
(`.prompt-stack`). That is not tidiness — all three used to be absolutely positioned against
the bottom edge at hand-chosen offsets, and they collided twice: first the two Enter chips
with each other, then the counter straight through the finish chip in a portrait window. A
flex column makes the overlap structurally impossible instead of a number somebody has to
keep right.

A tap cannot be recognised on keydown — you do not yet know it is a tap — so the tap action
fires on **keyup**, and the hold is counted in `_stepPlaying` off the key's down-state, since
auto-repeat is discarded and a held key fires keydown exactly once.

Two traps, both of which bit:

- **The latch.** Enter is how you dismiss the intro screen, so the press that *starts* a round
  is very often still down when the round begins. Without a latch that same uninterrupted press
  ticks the quit timer straight through and dumps you back to the title before you have moved.
- **Clear the latch on keyup, not only in the frame loop.** Clearing it on any frame where
  Enter is up sounds equivalent and is not: release and re-press inside a single frame and no
  frame ever observes the key up, so the latch stays set and hold-to-quit silently stops
  working for the rest of the round. `test-ui` found that one.

The hold is measured in **game time**, which is clamped to 0.1s per frame, so on a machine
rendering at 3fps the gesture takes longer than 0.9s of wall clock. That is correct — it is
also why every assertion about it in `test-ui` waits on state rather than on a stopwatch.

**Reset Progress** lives in Options. It clears the cleared-stage list, best sizes and the
collection log, and deliberately **keeps** volume, camera and quality settings — nobody asking
to replay the game is also asking to have the music turned back up to a level they already
rejected. It takes two clicks, because there is no undo and the button sits next to the
shadows toggle. It is not a browser `confirm()`: over a full-screen game that reads as a scam
popup, so the button arms itself instead and disarms after a few seconds of being ignored.

## A note on originality

This is a fan homage, not a port. The original game's soundtrack, sound effects, character
designs and logos are copyrighted and none of them are used here. What you get instead:

- **Original music**, composed for this project in the same idiom the original lives in —
  bossa nova and samba grooves, major sevenths and ninths, brass punctuation, wordless
  scat — and synthesised live from oscillators. A theme of its own for each of the
  eleven stages (the five cosmic ones run to sixteen bars, the rest to eight), a title vamp, a
  results fanfare. See `src/audio/songs.js` for the actual notes.
- **Original sound effects**, all synthesised: the rolling grind (which drops in pitch as
  you grow), pickup pops (pitched by how big the object was relative to you), impact
  thuds, size-up chimes, the countdown, and the royal gibberish voice.

- **Original text**, including the King's commentary and the ending.

## How it works

### Objects

Every prop is built by a function that stacks boxes, spheres, cylinders and lathes into one
merged, vertex-coloured `BufferGeometry` (`src/render/geom.js`). The whole game — terrain,
props, katamari — shares a single `MeshLambertMaterial`, which is what gives it a
consistent poster-paint look and keeps state changes at zero.

Each archetype's gameplay numbers are *derived from its geometry*, not hand-authored:

```
boxVol = w * h * d                    of the bounding box
volume = boxVol * fill                how much the katamari grows
pickup = cbrt(boxVol) * sizeMul       the size the game compares
```

An object sticks when `pickup <= diameter * pickupRatio` (**0.88**). That constant is the
cheapest lever on how long a stage lasts and the only one that does not move the size
ceiling — lowering it adds rungs to the ladder without changing how much there is to eat,
so you still finish the same size, just later. It sat at 0.78 for a long time because 0.88
was generous enough to send the city from 5m to its 300m ceiling in 90 seconds — but that
was measured while top speed still climbed steeply with size, so the two compounded. With
the speed curve flat they no longer do, and 0.88 is what pays for that flatness (see
[Movement](#movement)). Do not go much below 0.78 whatever the exponent is: measured at 0.60
the city stalls out at 26m and never reaches its goal, because the rungs get further apart
than one rung's growth can bridge. (`packing` also slows growth, but the
ceiling is `stageMass * packing`, so it drags the finish down with it. `npm run balance
-- --pickup=N --packing=N` tries either without editing the game.)

Using the geometric mean of the three dimensions for `pickup` reproduces a real behaviour
of the original: long slender things (pencils, planks, ladders) become collectable well
before their longest dimension suggests, and they stick out awkwardly until you bury them.

### Collision

Broadphase is a uniform grid; props are inserted into every cell their footprint touches,
so one skyscraper is found from any of them. Then two narrower stages.

**A vertical profile** — horizontal reach sampled into 8 height slices — is the cheap
reject and the pickup test. A street lamp's arm reaches 1.1m sideways at 4.3m up; with a
single bounding radius a small katamari slams into thin air and wedges itself, and with a
profile it rolls underneath. Profiles are sampled per *triangle*, not per vertex, because a
cylinder only has vertices at its end caps and vertex sampling leaves the whole middle of a
lamp post reading as zero radius.

**Collision parts** decide whether something is actually in your way. A profile is a reach
per height — one number per slice, measured from the centre — so it describes a solid disc
and cannot express a *hole*. A table's legs sit at its corners, so at leg height its profile
is a disc as wide as the whole table, and a katamari small enough to roll underneath is
stopped by an invisible wall 60cm out from the middle. Same for a chair, a bench, a swing
set, a bridge, a cow.

So every prop also carries up to 14 axis-aligned boxes, one per primitive its builder
stacked, captured before the geometry is merged into vertex soup. A part blocks you
horizontally **if and only if it overlaps you vertically** — which makes a table a top slab
you can ignore and four small rectangles with a lot of nothing between them. Simplification
drops any box already inside a bigger one (windows set into a wall) and absorbs the
leftovers into whichever kept box grows least; nothing is ever discarded, because a
collision volume that *misses* geometry lets you roll through a wall, which is a far worse
bug than a little phantom volume.

`npm run gaps` charges a katamari at things that should have gaps and at things that should
not, and `npm run underpass` lists every prop in the catalog with a reachable gap under it —
"reachable" meaning the gap is taller than the smallest katamari that will ever meet it. It
found the one real casualty of the change: a city bus body sits 50cm up on its wheels, the
town starts you at exactly 50cm, and buses had no side skirt. They do now.

### Growth and attachment

Growth is volumetric: `volume += object.volume * packing`, then radius from volume. Eating
something near your own size is worth about a quarter of your volume, which is why the
late game accelerates the way it does.

A collected object keeps its **absolute** size forever and is pinned to a fixed direction
in the ball's rotating frame. Each frame its radial distance is recomputed from the current
radius, so it rides the surface as the ball inflates and becomes proportionally smaller —
the same visual logic the original uses. Objects that become trivially small are retired.

Attachment points get a little angular scatter: contact points all lie in the plane you
happen to be rolling along, and without scatter the ball grows a neat equatorial belt of
junk and stays bald everywhere else.

### Movement

Top speed is **normalised per stage and square-root in diameter**, and velocity is
steered toward a target rather than emerging from a tug-of-war between thrust and drag:

```
topSpeed = stage.speed * (diameter / stage.startSize) ^ 0.56   // Options-settable

              small ->  huge      (lerped by progress through this stage)
accel  rate =  9.0  ->  1.30      gaining speed the way you are pushing
brake  rate =  9.0  ->  1.30      shedding it when you let go
turn   rate =  9.0  ->  1.30      scrubbing off sideways drift
                                  all x topSpeed, i.e. "top speeds per second"
```

The three are **identical on purpose**. Same mass, same force, whichever way you are
pushing — speeding up, slowing down and turning are one physical quantity seen from three
angles, and there is no reason for a katamari to be worse at one than another. They were
not identical for a while: brake sat at 62–67% of accel on the theory that coasting is what
mass feels like, which produced a ball that could get into trouble faster than it could get
out. That got reported as the game feeling like it got *faster* as the ball grew — which it
does not, and the measurements say so. What collapsed was **control authority**: stopping
distance ran from 0.5 to 3.8 of the ball's own widths across a stage, so late on you could
not be slow when you wanted to be, and being unable to shed speed reads exactly like having
too much of it.

#### The exponent, and the two cues that fight over it

This one number took five rounds of player feedback, and the thing that settled it was
working out **which of two speed cues players actually report**.

- **Ball-relative.** The camera pulls back in proportion to the katamari, so the ball
  covers a constant fraction of the screen and apparent motion is `v / (k·D)`, which sags
  as `D^(p-1)`.
- **World-relative.** Buildings, kerbs and road markings do *not* scale with you, so the
  rate at which scenery streams past is `v / spacing`, which grows as `D^p`.

The first version used one global curve, `2.2 · D^0.42`; the city took four minutes to
cross at its starting size. The second normalised per stage at `D^0.32`. Both were reported
as an unplayable late game — that is cue 1, and it is real. So the exponent went to 1,
where ball-relative speed is exactly flat. And the report came back: *"the speed keeps
increasing as I get bigger rather than scaling to the level"*, then, more precisely: *"it
should move at a static top speed relative to the environment; as it gets bigger it should
slow down."*

That is cue 2, and it is the one you get complaints about, because you steer by the world.
But it does not win outright — 0.25 shipped and came straight back: *"the slow down is WAY
too aggressive, there is no chance of completing even the first area."*

**0.5 is the balance point, and it is not a shrug.** Over a stage with growth ratio G, cue 1
is wrong by `G^(1-p)` and cue 2 by `G^p`, so they are equally wrong at exactly 0.5. It is
also where **stopping distance in ball-widths is exactly flat** — that goes as
`D^(p-1) / brakeMul`, and `48^-0.5 · 6.9 = 1.0` across the house's span. The katamari is
equally precise at every size while still taking 7× longer in seconds to do anything: heavy
in *time*, precise in *space*.

The one number that decides it is **how long it takes to cross the first room at goal size**,
because the end of a round is a search:

| exponent | house crossing at goal size | scenery speed-up over a stage |
|---|---|---|
| 0.75 | 5.7s | 13.5× — played, "increasingly faster and difficult to control" |
| **0.56** | **11.0s** | **7.0× — shipped** |
| 0.50 | 13.0s | 5.7× — played, "getting close" |
| 0.25 | 32s | 2.4× — played, "no chance of completing even the first area" |

It cannot be 0, and that is arithmetic rather than taste: at a constant speed, swept area per
second is `speed · D`, so `D² ~ t` and a stage costs time proportional to the *square* of its
growth ratio. The house grows 32× inside a 26m room; holding its speed constant and still
reaching 1m60 in six minutes needs about 3× the current speed, which for a 5cm marble means
crossing the visible floor in 0.15 seconds.

Measured clear rates (15 bot runs each, skill 0.9), house / town / city:

| exponent | house | town | city | |
|---|---|---|---|---|
| 0.00 | 2/15 | 0/15 | 15/15 | fully static — house and town never finish |
| 0.15 | 3/15 | 7/15 | 15/15 | still broken |
| 0.25 | 12/15 | 11/15 | 15/15 | played — far too slow to finish |
| 0.35 | 12/15 | 12/15 | 15/15 | |
| 0.50 | 12/15 | 14/15 | 15/15 | played — "getting close" |
| 0.53 | 14/15 | 9/15 | 15/15 | played — town clock also cut to 6:00 |
| **0.56** | **13/15** | **11/15** | **15/15** | **shipped** — town clock back to 7:00 |
| 0.60 | 14/15 | 13/15 | 15/15 | |
| 0.75 | 10/15 | 15/15 | 15/15 | played — reported as too fast |

⚠️ **The bot cannot see the failure that got 0.25 rejected.** It cleared the house 12 times
in 15 there — the same as at 0.5 — because it knows where every prop is. A player does not:
the end of a round is a *search*, and search time scales with how fast you cross the room. So
`balance` can tell you a stage is impossible, never that it is miserable. Weight the report
over the instrument on this one.

Lowering the exponent at all needed one enabling change: `pickupRatio` 0.78 → **0.88**.
Growth is mass swept per second and swept area is `speed · D`; flattening the speed curve
takes the `speed` term out of that product, so a big katamari covers far less ground and has
to get more out of the ground it does cover. At 0.78 and exponent 0.25 the house clears 2
runs in 15 and the town none at all.

**It is a player-facing setting now.** Options → *Speed as you grow* writes straight to
`TUNING.speedP` (0–100 maps to 0.0–1.0), persists only once actually moved (an untouched
saved value adopts whatever the current build ships, so returning players are not pinned to
an old default), and shows the crossing time and the
scenery speed-up for whatever you pick. After six round-trips on one constant, in both
directions, the honest conclusion was that it is a taste dial and belongs in the player's
hands. `npm run speedcurve` pins the wiring down.

**The three rates carry all of the weight**, because they are now the only things that
degrade. `progress` is how far through *its own stage* the katamari is
(`log(D / stageStart) / log(stageSpan)`), not its absolute size — using absolute size made
the city open sluggish, since 5m is "large" globally while being the smallest thing on that
map. Measured across a stage: time to reach top speed **0.11s → 0.73s**, and — being
symmetric — exactly the same to stop. Runway 0.0m → 1.2m in the house and 3.9m → 159m in
the city. A big katamari takes a long time to get going and a long time to turn — but with
the speed curve flat it does all of that within a fraction of its own width (coasting stays
at 0.1–0.5 ball-widths at every size), which is exactly the "heavy but not out of control"
the weight ramp was always aiming at and never quite hit while speed was climbing too.

There used to be a single exponential ground friction here instead, and it was doing three
jobs badly:

- It set the **stopping** rate. Legitimate — that is now `brake`.
- It shaped the **approach** to top speed. Legitimate — that is now `accel`.
- It also set **top speed**, because velocity settles where thrust and drag balance, at
  `topSpeed · accelMul / friction`. So two independent mechanisms capped speed and the
  lower one won silently. A pass that set `accelMulHuge` to 1.35 against a friction of 3.1
  quietly held the ball to 43% of its stated top speed when large — re-creating the exact
  bug the linear curve exists to remove, while every readout showed the higher number.

And because friction was a *constant* per-second decay, time-to-stop was **0.54 seconds at
every size**: a 300m katamari doing 1440 m/s halted as fast as a marble. Heaviness was half
implemented — slow to start, instant to stop — and coasting is most of what mass feels like.
Splitting the three rates fixes both problems at once. Top speed is now exactly top speed,
time to reach it is exactly `1/accelMul`, time to stop is exactly `1/brakeMul`, and no
constant can silently override another.

One other thing the speed rework broke and had to have retuned: **knock-off**. Objects
shake loose above `knockThreshold` × top speed, and at the old 1.02 a routine dash into a
building triggered it. Survivable at the old speeds; at the new ones the collision rate
overtook the pickup rate in a dense city and the ball visibly *shrank* over a few minutes.
It now sits at 1.42 — just under the 1.55 dash cap, so only a full-tilt slam costs anything
— with a 4-second immunity window and a hard cap of 1.5% of volume per knock.

`npm run speedtable` **measures** all of this by running the real katamari at full throttle
on empty ground and then letting go, rather than quoting the curve. Every problem in this
section was invisible in the formula and obvious in the measurement.

### Climbing

Being too big to stick to does not make something a wall. Anything whose top sits within
`climbFrac` (1.4) of a radius above your underside is a **ramp**, and what decides whether
you get over it is gravity: the rise is paid for out of kinetic energy at the honest rate
`v² → v² − 2gh`, so you need `v ≥ √(2gh)` to crest it. Charge it and you roll over; drift
into it and you stall on the slope and settle back. That turns the edge of the size ladder
from an invisible wall at exactly `pickupRatio` into something you can lean on, and it is
where the sensation of the world slowing you down is meant to come from — not from a drag
constant.

The height a part holds you at is the **tangency** solution, not the part's top: a sphere
of radius `r` whose centre is a horizontal distance `d` from the box rests where it just
touches the top edge, at `partTop + √(r² − d²) − r`. So it is lifted the full height only
when it is actually *over* the part, and not at all when it is merely touching the side.
And that lift only applies when the part's top is **at or below the ball's centre** — a
ball pressed against the side of something taller than its own centre is not resting on
anything.

Both conditions matter. Without them a 272m katamari in the city was jacked up the instant
it brushed a 225m hill, floated a mean of 118m off the ground, could not reach a single
thing beneath it, and hung there. The centre-height rule is also the honest physical limit
on climbing — a rolling ball cannot mount a step taller than its radius however fast it is
going, because past that the contact normal points down into the step and pushing only
wedges it harder. `climbFrac` can never buy more than that and should not try.

Standing on a prop has to be asked as a **separate question** from being blocked by one,
because the two are mutually exclusive by construction: once you have climbed on top of a
part it no longer overlaps you vertically, so the blocking test stops seeing it. A first
attempt that only answered the blocking question produced a ball that rode up an obstacle,
lost its support the instant it cleared the top, and dropped straight back down — a climb
that could never finish. And the stand test has to trigger on *touching*, not on being over
the middle, because the obstacle push holds a stopped ball at exactly one radius away, so
any stricter reach can never fire at all.

`npm run climb` picks props from the catalog at the exact size where each stops being
edible and checks both directions: fast gets over, slow does not.

### Where things go

An archetype's `surface` is `'land'` (the default), `'water'` or `'air'`, and stages declare
water with `w.water(x0,z0,x1,z1)`. `World.place` refuses to put a boat in a field or an
office block in a harbour, and lifts air props to their `flyHeight` above the ground; the
scatter passes retry until they find somewhere valid. Before this the map was one
undifferentiated sheet and anything could end up anywhere. Hand-placed landmarks that
knowingly straddle a shoreline — the lighthouse on its breakwater, the bridge spans — pass
`force` to opt out.

Restricting props to sensible ground has a knock-on: taking 437 objects out of the city's
harbour thinned the size ladder enough that `npm run balance` reported a gap at 86m → 140m,
which is a katamari that simply stops growing. The hills are the only rungs between the
stadium (83m) and the top, so they now sample that band with 26 copies across a wider scale
range. **Check `ladder gaps` after any change to what gets placed where.**

### Falling

Gravity is in **katamari radii per second squared**, not metres — `gravityRadii` (720),
which reproduces the old flat 18 m/s² at the house's 2.5cm starting radius.

Same argument as top speed. A flat metric gravity meant a 5cm ball dropped its own radius
in 0.05s and a 300m one took 4.1s: the same fall, five times slower to watch. Measured in
the city, a large katamari spent **30% of its time airborne** — and airborne means nothing
underneath is in reach, so it read as "I have to float down before I can pick anything up".
As a multiple of radius it is scale-invariant, a fall of one ball-width takes the same time
at every size, and the measured airborne fraction is now 0%.

Climbing is deliberately *not* gated against that gravity. Once `g` scales with the ball,
`v² ≥ 2gh` makes climbing ability depend on `(topSpeed/R)²`, which varies about 7× between
stages — the city would have been able to mount 2% of its own radius, which is not a kerb.
So the gate is written in ball-relative units directly: `rise ≤ climbFrac · R · (v/topSpeed)²`.
Falling is physics and should be scale-invariant; how far you can lean on the size ladder is
a game rule and should be authorable.

### Rolling and the camera

The ball's spin axis follows from rolling without slipping — the contact point has to be
stationary, so `omega = (v.z, 0, -v.x) / R`. This had the sign the other way round for a
while, which spins the ball backwards relative to travel. `npm run roll` tracks the speck of
katamari currently touching the ground and checks it does not move: 0× ball speed is
correct, 2× is exactly counter-rotating, and the broken version measured 1.999×.

Movement is camera-relative: the ground-plane basis is built explicitly from where the
rig is (`forward = -(sin yaw, cos yaw)`, `right = up x forward`) rather than by applying a
rotation matrix to the raw input. An earlier version did the latter with the X term's sign
flipped, which is equivalent to rotating by `-yaw`: correct at 0 and 180 degrees, exactly
backwards at 90 and 270. Because the camera starts at 180, W felt right until you turned.
`npm run controls` asserts every key at every angle against the real camera's
`getWorldDirection()`, so the same class of error cannot come back unnoticed.

The camera smooths **the point it follows, never the orbit around it**. Damping the
camera's world position instead makes every mouse movement arrive late, because swinging
the yaw moves the desired position and the rig then eases toward it — and tying that
damping rate to the katamari's speed (as it once did) made the lag vary with acceleration
and braking, so the camera felt heaviest exactly when you were trying to look around.
Distance is a function of size only now, for the same reason: it used to pull back with
speed, which meant the view crept in and out every time you touched the stick.

Floors are axis-aligned rectangles, optionally sloped. The katamari stands on the highest
one it can reach; anything more than about one radius above it is a wall instead. That one
rule gives the "once you're big enough you can get onto the tatami" progression for free.

### Rendering

One `InstancedMesh` per (archetype, variant, spatial chunk). Collecting an object
swap-removes its instance slot and decrements the draw count, so GPU work shrinks as you
roll. Archetypes that have become sub-pixel next to the katamari stop being drawn (they
stay collectable). Depth uses a logarithmic buffer because the katamari spans 5cm to ~270m,
and fog scales with your size so a small ball isn't rasterising a whole city it can't see.

Coplanar faces are the one thing this art style punishes. House roofs shimmered in blue and
brown stripes at distance because the roof wedge's flat underside and the top of the eaves
band both sat at exactly `y = H + 0.1` across the entire roof footprint — a large-area
depth tie that no depth buffer resolves consistently. The fix is to sink the wedge 4cm into
the eaves rather than rest it flush. Anywhere two large horizontal faces would land on the
same plane, overlap them instead.

Roughly 180–690 draw calls and 0.3–1.3M triangles per frame depending on stage.

### Balance, and why the bot is not the player

`balance.mjs` runs two different bots — one that chases the highest-value reachable object,
one that lawnmowers with heading momentum — over several seeds each, and reports **each
bot's median** before picking the better bot. Stage goals are set at roughly 60–75% of that
median; across the eleven stages it currently reads 73 / 61 / 63 / 77 / 61 / 64 / 66 / 65 /
65 / 67 / 64 percent, with 8–9 of 9 runs reaching the goal on every one.

Both of those design choices were bought with mistakes:

- **Report medians, not a single run.** Each bot is deterministic given a seed, so one run
  is one *path*, and a path responds chaotically to tuning. A single sweeper seed reported
  265m in the city and 90m after a 25% speed change — which looked exactly like "that speed
  broke the stage" and wasn't. Nine seeds show the sweeper actually lands in one of two
  attractors, ~110m or ~265m, at *every* speed from 12 to 33 m/s; which attractor it finds
  is seed luck. The speed question the sim appeared to answer, it could not answer at all.
- **Judge each bot separately.** Pooling both bots' runs into one median is meaningless,
  because on every stage one of them is simply unsuited to the shape — the lawnmower is
  hopeless in a 26m room, the targeter is hopeless across a 1km city. The pooled median
  measures "half of all strategies are bad", which was always true.

Two more things about the bots, recorded so nobody repeats them:

- Its stall detector originally measured progress in **diameters**. A 200m katamari covers
  well under one diameter per second even at full tilt, so every large ball read as stuck
  and the bot silently fell back to a random walk — which quietly invalidated every balance
  number for the late game while still printing a plausible-looking report.
- Its decision cadence was originally **time-based**. After the speed rework the city bot
  committed to a heading for 100–180m at a stretch and flew straight past everything. It
  now re-decides on distance travelled.

**And the biggest limitation is not a bug at all: the bot cannot see search cost.** It knows
where every prop is, so hunting for the next thing is free to it. A slow, sparse endgame on a
huge map costs it nothing and costs a player minutes. It can prove a stage impossible; it can
never notice one that is merely miserable. That is not fixable by tuning the bot — you would
have to model a player's ignorance — so instead it is handled by *not shipping the bot's
number* on the two stages where the blind spot bites hardest. The galaxy and the universe are
the largest maps in the game at 25,600 units across, and both carry more clock than the
harness asks for (11:30 against 10:00, 13:30 against 11:00). Adding that time moved neither
goal percentage, because the sweeper empties both stages before the clock runs out.

The one time this lesson was ignored, the report said 12/15 clears and the reply from the
person actually playing it was "there is no chance of completing even the first area". It cost
two rounds of retuning.

### The travel check the harness does not do

Every stage should let you cover a similar amount of its own map in the time it gives you.
That is not something `balance` measures, and it is the one number that explained the only
stage a player could not finish:

| stage | map | speed | seconds to cross at start size |
|---|---|---|---|
| atom | 52 | 0.68 | 76 |
| microbe | 32 | 0.42 | 76 |
| house | 26 | 0.34 | 76 |
| town | 192 | 2.53 | 76 |
| country | 25,600 | 320 | 80 |
| **quantum (was)** | **30** | **0.30** | **100** |
| **solar (was)** | **30** | **0.33** | **91** |

The quantum realm was the only small stage off the pattern. Everything in it took a third
longer to reach, which makes the round a third shorter in the only unit that matters — and
`balance` reported 9 of 9 clears throughout, because the bot knows where every prop is and
never wastes a metre. **The cost of a slow stage falls entirely on the player who has to
look.** Same shape as the search-cost blind spot, measured a different way.

`stage.speed` defaults to `stageWidth / TUNING.crossSeconds` when omitted. Any stage that
sets it by hand should be checked against this table. The city is a deliberate exception at
315s — it is authored small and stretched by `spread: 4`, and you cover its ground quickly
once you are large.

Bad simulator output that looks reasonable is worse than a crash. When a balance number
surprises you, suspect the harness before the game — and when a player and the harness
disagree, go looking for what the harness structurally cannot see.

## Things that are deliberately faithful

- The stage ends on the clock, not on the goal.
- Slamming into something huge at speed shakes objects loose (with a cooldown, so one bad
  corner isn't fatal).
- Long thin objects are collectable early and make you roll strangely.
- Size readout in `m` / `cm` / `mm`.
- The King is never quite satisfied.

## Things that are deliberately not

- Dual analog stick controls. This uses WASD + mouse.
- Cousins, presents, and the constellation meta-game.
- Anything at all from the original's asset files.
